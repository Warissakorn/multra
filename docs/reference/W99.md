## 1. Scope and sources

MULTRA's `w99` is a psycho-physical car-following model with the ten-parameter (CC0–CC9) structure
Wiedemann published in 1999. It is our own explicitly parameterised formulation, written from public
sources only:

- PTV's public [Wiedemann 99 parameter page](https://cgi.ptvgroup.com/vision-help/VISSIM_2025_ENG/Content/4_BasisdatenSim/FahrverhaltensparameterFolgeverh_Wied99.htm)
  (Vissim 2025 help, read 2026-11-23). It gives the vocabulary and units of CC0–CC9, the safety
  distance `CC0 + CC1 · v`, and the free acceleration: linear from CC8 at standstill to CC9 at
  80 km/h and constant above, plus a driver term `z` ~ N(0.5, 0.15) in [0, 1], capped by the vehicle
  type. It publishes no thresholds or decision tree, and no defaults except CC2's 4.0 m.
- [`glgh/w99-demo`](https://github.com/glgh/w99-demo) `js/model.js` (MIT, © 2016 glgh, commit
  `80eb392`, read 2026-11-23). It is the threshold set and decision tree below: `SDXc`, `SDXo`, `SDXv`,
  `SDV`, `SDVc`, `SDVo` and the four regimes, in that order.
- Eclipse SUMO's [`MSCFModel_W99`](https://sumo.dlr.de/doxygen/db/d3e/_m_s_c_f_model___w99_8cpp_source.html)
  (EPL-2.0 OR GPL-2.0-or-later). It credits that demo as its source and notes, in its header, that
  several W99 versions exist. This contract takes one rule from it: the slower-speed floor at 0 (§3).

It is **not** PTV's proprietary implementation and claims no equivalence with Vissim or SUMO results.
Values calibrated in Vissim do not transfer (rule 4); the not-yet-validated marker stays. Where the
sources disagree or the demo is dimensionally inconsistent, §4's *Deviations* says what this contract
does instead and why.

**Out of scope here:**
- CC1 as a per-driver distribution (Vissim 2025): first out of scope, then contracted by the owner's choice
  (§5a, D645), not yet implemented;
- halving the free acceleration for heavy vehicles (PTV): **decided not to (D644)**. The free
  acceleration is already bounded by the vehicle type's `maxAccelerationAt` (§6 step 1), as Vissim's
  per-type acceleration curves and SUMO's per-type `accel` bound every model; a heavy type's own limit
  (1.0 m/s² in `data/vehicle-types/heavy-vehicle.json`, beside 2.5 for the car) does the work, and a
  second factor would halve it twice;
- gradient effects and jerk limits;
- PTV's separate standstill distance at static obstacles;
- lateral behaviour, motorcycles, calibration and presets (§5).

## 2. Inputs, units and sign convention

All quantities are SI: m, s, m/s, m/s². Each follower is evaluated per tick, from the pre-motion
snapshot, through PERCEPTION §3. W99 receives each perceived leader as today's
`Leader{gap, speed, acceleration}`, the same inputs W74 receives (W74 §2).

| Symbol | Meaning |
|---|---|
| `v` | Follower speed |
| `vDes` | Sampled `desiredSpeed` |
| `aPrev` | The follower's published acceleration from the previous tick (`Vehicle::acceleration`, after every clamp of that tick); 0 for a vehicle being inserted |
| `g` | Net gap: the obstacle's rear minus the follower's front (`Leader::gap`) |
| `vL`, `aL` | Obstacle speed and acceleration; a static obstacle has `vL = aL = 0` |
| `dv` | `vL − v`, **negative when closing**. This is W99's sign, the opposite of W74's `dv` |
| `zW` | Per-driver trait in [0, 1) (§5) |
| `df` | The existing `driverFactor` (DRIVER_FACTOR, D236) |

The demo writes `dx` as the gap between the leader's rear and the follower's front, so `g = dx` and
CC0 is a standstill *net* gap. No leader length appears anywhere. SUMO's own `gap2pred` excludes its
`minGap`, so it adds the gap back; MULTRA's `Leader::gap` does not exclude it.

## 3. Thresholds

```
vSlow = v                         if dv ≥ 0 or aL < −1 m/s²
        vL + dv · (zW − 0.5)      otherwise
SDXc  = CC0                       if vL ≤ 0          (a standing or static obstacle)
        CC0 + CC1 · max(0, vSlow) otherwise          (desired minimum following gap)
SDXo  = SDXc + CC2                                   (maximum following gap)
SDXv  = SDXo + CC3 · (dv − CC4)                      (where closing starts)
SDV   = CC6 · 10⁻⁴ · g²                              (perception of speed difference)
SDVc  = CC4 − SDV                 if vL > 0, else 0  (closing threshold)
SDVo  = SDV + CC5                 if v > CC5, else SDV (opening threshold)
```

- `max(0, vSlow)` is SUMO's. The demo leaves it out and marks the case with a comment: a fast
  follower behind a slow leader can give `vSlow < 0`, and then `SDXc < CC0`.
- **Fixed constants:** `−1 m/s²` (a leader braking harder than this is taken as braking), the `10⁻⁴`
  scale of CC6 (it keeps Vissim's displayed number) and 80 km/h (CC9's definition). These are the
  model's structure, as W74's `0.1` under the root is, not tunable content (rule 5).

**Ordering guaranteed by §5's ranges** (`CC4 ≤ 0 ≤ CC5`, `CC6 ≥ 0`):

- `SDVc ≤ SDVo`, so `dv < SDVc` implies `dv < SDVo`.
- `SDXc ≥ CC0 > 0`.

## 4. Regimes and accelerations

Classification, evaluated top to bottom; the first match wins:

| # | Condition | Regime (demo code) | `FollowingMode` |
|---|---|---|---|
| 0 | No obstacle | free | `free` |
| 1 | `dv < SDVo` and `g ≤ SDXc` | too close (A) | `braking` |
| 2 | `dv < SDVc` and `g < SDXv` | closing (B) | `approaching` |
| 3 | `dv < SDVo` and `g < SDXo` | following (f) | `following` |
| 4 | otherwise | free (w) | `free` |

**Equality sides are part of the contract:**

- `g = SDXc` is too close.
- `dv = SDVo` is not too close and not following.
- `dv = SDVc` is not closing.
- `g = SDXv` is not closing.
- `g = SDXo` is free.

**Accelerations** (before §6's bounds):

- **Too close.** If `v = 0`, then `a = 0`. Otherwise start from `a₀ = 0`, and if `dv < 0`:
  - when `g > CC0`, `a₀ = min(aL + dv² / (CC0 − g), aPrev)`;
  - otherwise `a₀ = min(aL + 0.5 · (dv − SDVo), aPrev)`.

  Then `a = −CC7` if `a₀ > −CC7`, else `a = a₀`. The driver always brakes at least by the
  oscillation acceleration.
- **Closing.** `a = 0.5 · dv² / (SDXc − g − 0.1)`. By §3's ordering, row 2 is reached only with
  `g > SDXc`, so the denominator is at most −0.1 m. The division is exact and `a ≤ 0`; no tolerance
  is introduced.
- **Following.**
  - `aPrev ≤ 0`: `a = min(aPrev, −CC7)`.
  - Otherwise: `a = max(aPrev, CC7)`.

  The driver keeps the sign it had, at least ±CC7, until a threshold moves it to another regime.
- **Standstill in following (ours).** With `v = 0` the following rule is `a = max(aPrev, CC7)`.
  Without it, a vehicle that brakes to rest in the band `(SDXc, SDXo)` behind a static obstacle
  (`dv = 0` for ever) keeps `aPrev ≤ 0`, never leaves the regime, and can rest up to CC2 short of a
  Stop line that is then never served. This is W74 §7's standstill rule, for the same reason. It
  creeps at CC7 until `g ≤ SDXc`, where *too close* holds it. D105 still forbids the creep when
  `g ≤ CC0`.
- **Free.**
  - With an obstacle and `g ≤ SDXc`: `a = 0`.
  - Else if `v ≥ vDes`: `a = 0`. The tick's desired-speed cap does the rest, as in W74.
  - Otherwise, with `aMax = CC8 + (CC9 − CC8) · min(v, 80/3.6) / (80/3.6) + df`:
    - with an obstacle and `g < SDXo`: `a = min(dv² / (SDXo − g), aMax)`;
    - else `a = aMax`.

**Deviations from the demo, each with its reason:**

| Demo | This contract | Why |
|---|---|---|
| `aMax = cc8 + cc9 · min(v, 80/3.6) + rand` | Linear CC8 → CC9 over 0–80 km/h, plus `df` | The demo's product has units of m²/s³ and reaches 35 m/s² at 80 km/h. PTV's text defines the linear form |
| Too close: `max(a, −10 + 0.5 · √v)`; closing: `max(a, −10)` | Neither; §6's `−type.maxDeceleration` bound | Hard rule 5: no code constant for a type's limit |
| `min(a, vDes − v)` in following and free | The tick's desired-speed cap | The demo compares m/s with m/s², a one-second horizon by accident |
| Free reads `status === 'w'` (always false: `status` is an object) | No such branch | Dead code in the source |
| `vSlow` may be negative | `max(0, vSlow)` | SUMO's floor; keeps `SDXc ≥ CC0` |
| Following at `v = 0` keeps `aPrev ≤ 0` | Standstill creep (above) | A Stop line must stay reachable (W74 §7's reason) |
| Per-driver `rand` reused for `vSlow` and `aMax` | `zW` for `vSlow`, `df` for `aMax` | PTV names `z` ~ N(0.5, 0.15) for the acceleration, which is `driverFactor`. A separate `zW` keeps the two independent |

**No regime uses a time constant.** `followingTime` and `speedThreshold` do not exist on a `w99`
behaviour.

## 5. Parameters and trait

### Parameters (hard rule 5: data, never code defaults)

A `model: "w99"` behaviour carries **every** key below. A missing, non-finite or out-of-range value
rejects the catalog or document atomically (`INVALID_BEHAVIOUR_PARAMETER`, path to the key). Key names
are Vissim's, lower-cased; they are never translated.

- Prototype keys and W74's eighteen keys are refused on a `w99` behaviour, and `cc*` keys are refused on
  a prototype or W74 one (`EDIT_UNSUPPORTED_FIELD`).
- No key is an alias of another model's: `cc0` is not `ax`, and `cc1` is not `followingTime`.

| Key | Unit | Range | Role |
|---|---|---|---|
| `cc0` | m | > 0 | Standstill net gap |
| `cc1` | s | ≥ 0 | Gap time in `SDXc` |
| `cc2` | m | ≥ 0 | Following oscillation: `SDXo − SDXc` |
| `cc3` | s | ≤ 0 | Where closing starts (`SDXv`) |
| `cc4` | m/s | ≤ 0 | Negative following threshold |
| `cc5` | m/s | ≥ 0 | Positive following threshold |
| `cc6` | 10⁻⁴ 1/(m·s) | ≥ 0 | Distance dependence of `SDV` |
| `cc7` | m/s² | > 0 | Oscillation acceleration. Above 0, so *too close* always brakes and the standstill creep moves |
| `cc8` | m/s² | > 0 | Free acceleration at standstill. Above 0, so a stopped driver with `df = 0` can start |
| `cc9` | m/s² | ≥ 0 | Free acceleration at and above 80 km/h |

- **Optional on `w99`:** `maxDecelerationCooperativeBraking` (same meaning, a bound).
- **Refused on `w99`:** the discretionary keys (D95/D101), as on `w74` in its first slice. No W99
  lane-change incentive is defined.
- **Type limits remain the type's:** `maxAcceleration` and its curve (START_UP, D608),
  `comfortableDeceleration`, `maxDeceleration`, length and desired-speed range.
- **No preset ships with this contract.** A cited one (D178) is its own slice. The demo's
  `W99_ORIGINAL` (1.50, 1.30, 4.00, −12.00, −0.25, 0.35, 6.00, 0.25, 2.00, 1.50) are the **fixture
  values** for §8's cases, not a preset.

### Driver trait

| Trait | Distribution | Source |
|---|---|---|
| `zW` | Uniform [0, 1) | Hashed, W74 §5's `u(i)` with index **15**: one past W74's 0–14, so a vehicle carrying both models' traits has independent draws |
| `df` | As today | The existing `driverFactor`; no new draw |

The hash, its integer arithmetic, the seed (`SimState::seed`, before the zero remap) and `perInput`'s
`traitIdentity` are W74 §5's, unchanged. `zW` is computed once at generation and stored with the
pending vehicle when the canonical scenario holds any `w99` behaviour. It is never redrawn while a
record waits, and it never touches `SimState::randomState`, so legacy runs keep their exact draw order
(BA18). **Implemented (D641):** `w99Trait` in `src/core/w99.*` over W74's factored `w74Uniform`;
`PendingVehicle::w99Trait`, set when `ScenarioIndex::w99`; checkpoints write `w99Trait` only when present
([evidence](../evidence/w99-traits.md)).

### CC1 as a distribution (§5a, D645; codec D646, draw D647, dialog D648)

The owner chose it on 2026-11-24 ("ok แบบกราฟสะสม เริ่มสัญญาเลย"): CC1 may be one number or a cumulative
curve that draws one value per driver, and the dialog offers the curve first. Vissim's recent versions let
CC1 reference a time distribution; a preset citing one must give the manual's page (D178).

**The key.** A `w99` behaviour carries **exactly one** of:
- `cc1`: a number, as today (≥ 0 s);
- `cc1Curve`: an array of `{"value": s, "share": 0..1}` points, with
  - two or more points;
  - values ≥ 0 and strictly increasing;
  - shares never decreasing, the first 0 and the last 1.

Both or neither is `INVALID_BEHAVIOUR_PARAMETER` at `<path>.cc1`. A bad point is the same code at
`<path>.cc1Curve[i].value` or `.share`. A flat stretch holds no drivers; a steep one holds many. This is
SPEED_DISTRIBUTION §2's rule, with `value` for `speed`.

**No default values.** The file never has an implicit mode: `cc1` or `cc1Curve` is written. "Default
random" is the dialog's: choosing *W99* starts CC1 in *Distribution* mode with an **empty** curve, and
Confirm refuses it until the author enters points or fills them from a cited preset. *Fixed* takes one
number, as today. Opening a behaviour shows the mode its file holds.

**Schema.** `cc1Curve` is allowed from the next schema version after 85 (its floor, set when the codec
lands). It is written, and that version selected, only when an owned `w99` behaviour uses it. A file
below the floor carrying it is refused (`EDIT_UNSUPPORTED_FIELD`). Fixed-`cc1` files
stay at 85, byte for byte.

**The draw.** `uCC1 = u(16)`, W74 §5's hash at index **16**, one past `zW`'s 15. It is drawn at
generation, only when the canonical scenario holds a behaviour with `cc1Curve`, and is stored on the
pending vehicle. It never touches `randomState`.

The driver's CC1 on a curved behaviour is the curve's inverse at `uCC1`:
- find the segment with `share_i < uCC1 ≤ share_{i+1}`;
- interpolate linearly;
- `uCC1` at or below the first share gives the first value.

This is SPEED_DISTRIBUTION §3's rule, shared rather than copied. The two-point curve `(a, 0), (b, 1)` gives
`a + uCC1 · (b − a)` to the bit.

**One share per driver.** The *share* `uCC1` is the driver's, not the value. Moving onto another `w99`
behaviour with a different curve, the same driver sits at the same quantile of that curve. On a fixed
behaviour the share is unused.

**Composition.** `follow` passes `w99Acceleration` the behaviour's parameters with `cc1` replaced by the
driver's value. Nothing else in §3–§4 changes. The accessor `desiredGap` (§6) reads the same driver
value: its callers pass the driver's share where they now pass the driver factor. `standstillGap` stays
`cc0`.

**Implemented (D646, D647).** The codec (D646): `W99Parameters::cc1Curve` (`cc1` is 0 and unused beside it),
the parser, the writer (the curve in `cc1`'s place), schema 86 (`w99Cc1CurveVersion`,
`rejectW99Cc1CurveBefore86`), the composed schema's `w99Cc1Point`, and `w99ParameterIssues` on the points.
The draw and composition (D647): `w99Cc1Share` (index 16) on `PendingVehicle::w99Cc1Share` when
`ScenarioIndex::w99Cc1Curve`, a checkpoint key only when present; `w99Cc1At` over the shared
`cumulativeInverse`; `w99DriverParameters` gives `follow` and `desiredGap`/`stopLineReach` the driver's CC1
([evidence](../evidence/w99-cc1-draw.md)). D646's interim Run refusal is gone. The behaviour dialog still
declined to open a curved behaviour until BA237. The dialog (D648): a *CC1* choice of *Fixed* or
*Distribution (per driver)*; a behaviour switched to W99 starts in Distribution with an empty table; the
table takes `cc1` in s and the cumulative share in % (as the desired-speed table), with Add and Remove;
Confirm names an empty table, a non-number cell or a point the validator refuses (`cc1Curve[i].share`).

**Rows.** BA233–BA237 in the delivery plan:
1. codec and its schema floor (BA233);
2. draw, rule and composition (BA234–BA236);
3. the dialog's mode and curve table (BA237).

One per session, after or beside BA231. The unvalidated marker stays, and no curve ships.

## 6. Composition with the shipped tick

`w99` replaces only step 4's acceleration, through the same dispatcher `follow(...)` W74 uses
(W74 §6). After it, the tick's order is unchanged and none of these steps is weakened:

1. clamp to `[−type.maxDeceleration, type.maxAcceleration(v)]`;
2. D105 (a stopped vehicle with `g ≤ CC0` gets no positive acceleration);
3. ballistic `integrate`;
4. the desired-speed cap;
5. the `allowedDistance` hard cap, with a counted `safety-clamp`;
6. Stop rest;
7. phase-2 request resolution.

| Accessor | `w99` |
|---|---|
| `standstillGap(b)` | `cc0` |
| `desiredGap(b, df, v)` | `cc0 + cc1 · v` (`SDXc` with `vSlow = v`) |

These accessors serve the same readers W74 lists:
- source insertion and D108;
- receiving space and waiting room;
- `stopLineReach`.

Multi-anticipation (PERCEPTION §3) calls `follow` once per perceived leader and keeps the minimum.
Hypothetical evaluations (lane-change own and trailing checks, the courtesy and cooperative second
obstacle, the D108 first step) read the vehicle's `aPrev` and `zW` and write nothing.

**Implemented (D642).** `follow` takes `previousAcceleration` (`Vehicle::acceleration`; 0 at insertion)
and dispatches to `w99Acceleration` with `zW`, returning no W74 state; the accessors above; the prototype's
standing-body floor (D583) skips w99 as it skips W74 ([evidence](../evidence/w99-composition.md)).

## 7. State and model switch

W99 adds **no new state**. Its only memory is `aPrev`, which the tick already publishes for every
vehicle. `FollowingResult` and its reaction FIFO entry (PERCEPTION §5) are unchanged: they carry
`w74` empty on a `w99` decision.

- **Entering `w99`.** `aPrev` is whatever the previous tick published, under any model, so the switch
  is continuous. An inserted vehicle has `aPrev = 0`.
- **Leaving `w99`.** Nothing to clear.
- **Selection** stays `effectiveBehaviour` (the front's segment at the pre-motion snapshot). The
  obstacle's model never matters: a follower reads only gap, speed and acceleration.
- **With `reactionTime`.** The applied FIFO entry's acceleration is what publishes, so `aPrev` is the
  delayed driver's last applied action, as it should be.

## 8. Timestep, numerics and hand-checked cases

depends on `dt ∈ (0, 0.5]`. As W74 did (BA27), the contract records that sensitivity (BA231) rather
than bounding it: [recorded](../evidence/w99-discharge.md) (D649). Unassigned, prototype-only and W74-only scenarios compile and run byte-identically
(BA18).

Fixture values: `W99_ORIGINAL` (§5), `zW = df = 0.5`, `vDes = 30 m/s`, and `aL = 0` unless stated.
Each value was checked by hand and by a scratch transcription of §3–§4. BA224 pins them to 10⁻¹²:

## 9. Persistence (the codec slice)

- **Schema version.** `model: "w99"` is written only when some owned behaviour has it, at the next free
  schema version when that slice lands. Below it, a file carrying `"w99"` is refused
  (`UNSUPPORTED_BEHAVIOUR_MODEL`), as is any unknown model. External catalogs in
  `data/driver-behaviour/` take the same `model` value.
- **Key names** live once, in a `w99ParameterKeys()` beside `w74ParameterKeys()`, read by the parser,
  the serializer, §5's range check and the composed project schema's behaviour row (D563's pattern).
- **Until composition** (BA230), Run refused a `w99` behaviour that any vehicle type or road selection
  named (`UNSUPPORTED_BEHAVIOUR_MODEL_RUN`, D639), as D136 did. Lifted by D642.
- **The Driving behaviours dialog** gains *W99* beside Prototype and W74: one empty field per key, no
  code default, and Confirm checks every key (D139's pattern). It is its own slice (D639, as W74's D139
  followed D136). **Implemented (D640):** the W74 and W99 rows share one key-field builder; switching model
  drops the other's keys; a prototype source is the library's first behaviour of neither model; the
  behaviour lab refuses Apply to a `w99` behaviour, as to a `w74` one.
- **Implemented (D639).** Schema 85 (`w99ModelVersion`). Run's refusal is `validateScenario`'s (a vehicle
  type or a compiled road assignment naming the behaviour), and `runDiagnostics` adds the road case
  (`w99RoadRunIssues`), which its runtime rows do not compile.
